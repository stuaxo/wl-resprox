# Debugging Scratchpad

## Crucial Environment Variables

When running apps or the proxy, these will be our best friends:

- `WAYLAND_DEBUG=1` - Dumps all Wayland protocol messages (Requests and Events) to stderr.
- `WAYLAND_DISPLAY=wayland-X` - Forces the client/proxy to connect to a specific socket.
- `RUST_LOG=debug` - Standard Rust tracing for our proxy logic.

## Tools

- `wayland-info` - Good for verifying which globals our proxy is successfully passing through.
- `wev` - Wayland event viewer. Good for testing if keyboard/mouse inputs are surviving the proxy translation.
- `strace -e trace=sendmsg,recvmsg -s <N> -o <file>` - syscall-level ground truth for "what bytes actually crossed the wire," used repeatedly earlier in this project's history (the new_id-gap bug, the partial-write bug) to settle disagreements between what we *believe* we sent and what a real peer *received*. Not installed in the container image by default (`apt-get install strace` as root) -- reach for it when log-level (`RUST_LOG=debug`) evidence alone isn't conclusive, e.g. a real compositor genuinely not responding vs. a hang on our own end.

- Host `gnome-shell` restart behavior: Running `pkill gnome-shell` on the host machine caused the login screen to temporarily disappear, followed by a momentary flash of existing windows before the shell fully recovered.

- 2026-07-29: Chased down the `/dev/dri/renderD128: Permission denied` blocker for `gtk4-demo` inside the nested labwc. Root cause turned out to be two separate, stacked problems — device permissions were never actually the whole story:

  1. **`sudo` inside the rootful container required a real TTY, blocking all non-interactive automation.** The container ships `sudo-rs` (Ubuntu 26.04's Rust reimplementation of sudo), which enforces `Defaults use_pty` unconditionally — even with a `NOPASSWD` rule in `/etc/sudoers.d/`, `sudo` still refused with "a terminal is required to authenticate" when run from a session with no controlling tty. Commenting out `Defaults use_pty` in `/etc/sudoers` (not just adding NOPASSWD) was required to unblock non-interactive `sudo`. A `NOPASSWD` drop-in file also has to sort *after* the existing `/etc/sudoers.d/sudoers` file alphabetically (e.g. `zz-*`, not `90-*`) — sudoers uses the last matching rule, and the stock file's `%sudo ALL=(ALL:ALL) ALL` (no NOPASSWD tag) comes after a numerically-prefixed drop-in and silently re-requires a password.

  2. **`podman exec --user=stu` (what `distrobox enter --root` does under the hood) does not apply supplementary/secondary groups from `/etc/group` at all** — it only sets the primary GID from `/etc/passwd`. So `usermod -aG video,render stu` run after container creation is silently ignored by every subsequent exec session: `id stu` (an NSS lookup) correctly listed `video`/`render`, but the *actual running process's* `id` (no argument) did not, and `/dev/dri/renderD128` stayed `Permission denied` even though the device's own ownership (`root:render`, mode `0660`) and `stu`'s `/etc/group` membership were both correct. Explicitly overriding the group at exec time — `podman exec --user stu:render ...` — works reliably.
     - Tried the "proper" fix: recreating the container with `--group-add 991 --group-add 44` baked in at `distrobox create` time (now in `scripts/setup-env.sh`). Verified in isolation on a **bare** `podman run --group-add ... --privileged` container that this does make `exec --user=<name>` (no override) pick up full supplementary groups correctly, including newly-`usermod`'d ones.
     - It does **not** work the same way inside a distrobox-managed container, though — confirmed with a completely fresh test user (`useradd` + `usermod -aG render`, no distrobox-specific setup) created *inside* `wayland-proxy-dev` after the group-add fix: still only got `groups=<primary>,0(root)` on exec, identical to `stu`. `/etc/group`, `/etc/gshadow`, and `/etc/passwd` all looked structurally normal (checked with `cat -A`, no encoding/formatting issues), and a container restart didn't change anything. This looks like a genuine, unresolved podman/distrobox interaction bug rather than a config mistake on our end — not root-caused further since the explicit-override workaround is reliable. Worth revisiting if this becomes annoying enough to chase properly.
     - **Practical upshot: `distrobox enter --root wayland-proxy-dev` alone still does NOT get GPU access.** Anything needing `/dev/dri` (nested labwc, GTK apps rendering via EGL) must be invoked with the explicit group override, e.g.:
       ```
       sudo podman exec --user stu:render wayland-proxy-dev <command>
       ```
       (`playbook.yml` still sets up the `video`/`render` groups properly via Ansible — that part is correct and necessary, just not sufficient on its own for `distrobox enter` sessions specifically.)

  - Once both were worked around, `labwc -C /dev/null` started cleanly (new `wayland-N` socket, no errors) and `gtk4-demo` ran against it with no permission/EGL errors — only benign `Portal operation not allowed` warnings from the missing `xdg-desktop-portal` in this minimal headless setup.

- 2026-07-29 (follow-up): Root-caused *why* `sudo` as `stu` never has a working password in the first place — this was the thing actually catching manual attempts to run `scripts/setup-env.sh` interactively ("caught by the password thing again"). It's not a "set a password on first entry" step at all (the old comment in `setup-env.sh` claiming that was wrong/never verified) — there is no such interactive step in distrobox's tooling.

  What actually happens: distrobox's own container-init script (`/usr/bin/entrypoint`, baked into the image, not our code) unconditionally clears `stu`'s password on first container boot (`chpasswd -e` with an empty encrypted field — shows as `passwd -S stu` → `NP`, "no password"). For rootful containers it then just locks `root` (`usermod -L root`) and stops there — it never leaves `stu` with a working credential *or* a `NOPASSWD` sudoers rule. Net effect: the very first `sudo` call as `stu` (e.g. `setup-env.sh`'s own `apt-get`/`ansible-playbook` step, or any manual `sudo` in an interactive `distrobox enter --root` shell) hits a real `[sudo] password for stu:` prompt that **no password can satisfy**, because none was ever validly set. Typing anything — including guesses, blank enter, the host's own password — fails identically, which is exactly the "maybe I'm setting it to something unknown" symptom.

  Fix, in the standard "disposable dev container" style (same pattern most devcontainer base images use for their default user):
  - `scripts/setup-env.sh` no longer goes through `distrobox enter --root` (as `stu`) for provisioning at all — it now runs `apt-get`/`ansible-playbook` directly via `sudo podman exec <container>` (container root, no `--user`), sidestepping `stu`'s broken sudo entirely for automation. (Also had to add an explicit `sudo podman start` before this — `distrobox create` only creates the container, doesn't start it, and a short poll loop waiting on `podman exec ... true` before the container's own init/apt-get finishes.)
  - `playbook.yml` has a new task, `Allow stu passwordless sudo`, that writes `/etc/sudoers.d/zz-stu-nopasswd` (`stu ALL=(ALL) NOPASSWD: ALL`, validated via `visudo -cf` — confirmed sudo-rs supports `-cf` on a specific file, not just the main `/etc/sudoers`). Filename deliberately sorts after the stock `sudoers` drop-in for the same last-matching-rule reason noted above. This is what actually fixes things for *your own later interactive* `sudo` use inside `distrobox enter --root` — confirmed working (`sudo true` succeeds, no prompt, even though `passwd -S stu` still correctly shows `NP`).
  - Verified the full fresh-container flow non-interactively end to end after this fix: `setup-env.sh` (9/9 ansible tasks OK) → `start-host.sh` → `start-guest.sh` (nested `labwc` starts clean, no permission errors) → `gtk4-demo` renders with only the same benign portal warnings as before.

- 2026-07-30: Root-caused the intermittent `wl_display.error: invalid arguments for wl_registry#2.bind` bug that had survived the partial-write fix, the busy-loop fix, and disproved both the message-batching and message-pacing theories (see earlier same-day entries above this one in the raw log -- summarized here since this is the entry that actually closes it out).

  **Root cause**: not a wire-encoding bug at all. labwc/wlroots (via libwayland-server) requires a client's `new_id`-allocating requests to arrive without gaps. Our relay silently *drops* any request on an object whose interface isn't in `interfaces.rs`'s lookup table (deliberately, to avoid misattributing fds on a message we can't parse -- see that file's doc comment). Real clients routinely send such a request immediately after binding a global we don't recognize (e.g. `zwp_linux_dmabuf_v1.get_default_feedback` right after binding `zwp_linux_dmabuf_v1`) -- and if that dropped request carried a `new_id`, the compositor never learns about that id, leaving a gap. The *next* new_id-bearing message we forward (another bind, a `sync`, whatever) then gets rejected as "invalid arguments," even though it's byte-perfect on its own.

  Confirmed with a small throwaway diagnostic client (`examples/probe_bind.rs` -- connects as a real Wayland client, binds a chosen set of globals in one burst, checks for `wl_display.error`) run against real labwc:
  - Binding several recognized-and-unrecognized globals together, no interleaved follow-up requests: always passes.
  - Same binds + an interleaved follow-up on an unrecognized interface (which we drop): fails.
  - Same binds + an interleaved follow-up on a *recognized* interface (which we forward): passes.
  - A bare client-side new_id **skip** with zero proxy involvement at all (`SKIP` token in the probe, burns an id, sends nothing): fails identically. This isolated it conclusively -- it's the gap itself, not our drop logic specifically, that labwc objects to.

  **Fix**: expanded `interfaces.rs` coverage so far fewer real-world globals hit the drop path at all. Added three more crates from the same smithay/wayland-rs family -- `wayland-protocols-wlr` (wlroots' own extensions: layer-shell, screencopy, gamma-control, etc. -- never went through freedesktop's official process, hence a separate crate from `wayland-protocols`), `wayland-protocols-plasma` (KDE's `org_kde_kwin_*`), and `wayland-protocols-misc` (orphaned-but-widely-used ones that fit neither bucket: `zwp_input_method_manager_v2`, `zwp_virtual_keyboard_manager_v1`) -- plus enabled `wayland-protocols`' own `staging`/`unstable` features, which were off. Went from 7 resolvable interfaces (core wayland.xml + xdg-shell only) to 46. Only top-level bindable globals need a table entry; child objects created by typed requests (e.g. `get_default_feedback` -> `zwp_linux_dmabuf_feedback_v1`) resolve automatically through that request's static `MessageDesc::child_interface`, never through this table.

  Added `interfaces::tests::resolves_every_global_observed_from_real_labwc`: a hardcoded list of every global a real run against labwc 0.9.3/wlroots 0.19.2 actually advertised, asserting each resolves. This is a plain `cargo test`, no live compositor needed -- it's meant to fail loudly the next time a real desktop's global list outpaces this table, instead of the silent per-message drop that caused this whole bug.

  Verified: all 18 tests pass; the exact probe scenario that reproduced the bug now passes; 15/15 clean `wayland-info` runs against real labwc with zero warnings/errors in the proxy log (previously deterministic 15/15 *failure* right before this fix).

  For the standing design of `interfaces.rs` itself -- what it covers, the gap-1/gap-2 framework, what's still open, and what improvements were considered but deferred -- see `docs/architecture-notes.md` rather than duplicating that here; this entry is the investigation log, that file is the reference that outlives it.

- 2026-07-30: First live-recovery test against real labwc (`shadow-table-1to1` branch's reconnect work, tasks 6-13 all passing in isolation via fake-compositor tests) hit a genuine hang: `recover_state_after_reconnect` sends `get_registry`+`sync` to the freshly-reconnected real compositor and never observes a response, stuck indefinitely (confirmed via `RUST_LOG=debug` -- "compositor reconnected -- recovering state" logs, then nothing for 30+ seconds, `gtk4-demo` still alive but frozen forever instead of recovering).

  **Crash method used**: `kill -9` on the `labwc` process directly (not `scripts/test-crash.sh`, which does the same thing but bundles it with its own harness). Then a *second* `labwc -C /dev/null` process started manually, targeting the same socket name the first one used (`wayland-0` in this run) after removing its stale socket/lock files, to simulate "the same compositor restarting" rather than a supervisor picking a fresh display name.

  **Why this matters going forward**: `kill -9` is the crudest possible crash -- instant, no cleanup, guaranteed `ECONNRESET`/EOF on the socket. It's not the only real-world failure mode (a compositor could also hang without closing the socket, crash mid-write leaving a partial message, or exit cleanly). Worth eventually formalizing a small matrix: {crash method} x {how the proxy is expected to detect it} x {which debugging tool actually shows what's happening} -- rather than continuing to improvise one scenario at a time. Not done yet; noting the gap rather than solving it now.

  Root cause of the hang itself not yet found -- next step is `strace` on the proxy process (see Tools above) to see whether `get_registry`/`sync` actually leaves our socket at all, since all the fake-compositor integration tests that exercise this exact code path pass reliably, meaning either something about a *real* compositor's response differs from our fakes, or something about this specific container/socket setup (freshly rebuilt Containerfile-based container, not yet proven for this exact scenario) is the actual variable.

- 2026-07-30 (follow-up): `strace -f` on the proxy binary itself (wrapping from launch, not attaching -- `ptrace(PTRACE_SEIZE, ...)` on an already-running PID fails with `Operation not permitted` under this container's yama ptrace_scope) found three real bugs, all in `shadow-table-1to1`, none caught by any fake-compositor test:

  1. `ShadowTable.next_host_id` never reset across reconnects. A fresh host connection is a brand-new `wl_client` to the compositor, requiring gapless allocation from 2 -- same rule as the earlier new_id-gap bug, just via the allocator this time. First real message after reconnect used some arbitrary high id (161 in the reproducing run); labwc rejected `get_registry` outright and closed the socket.
  2. The registry-collection loop's `host.fill().await?` didn't check for `Ok(0)` (EOF) -- `?` doesn't catch it, it's not an `Err`. Once (1) made labwc close the connection, this spun at 100% CPU calling `recvmsg` forever (2.6M+ lines in the trace).
  3. Fixing (1) safely required making `host_id`/`guest_id` generation-aware (reject stale mappings that could numerically collide with fresh ones -- both compositor instances' allocators restart from the same baseline). That broke `wl_display`'s own 1:1 mapping, seeded once at `ShadowTable::new()` and never touched again -- every message references `wl_display` via `sync`/`get_registry`/`delete_id`, so this broke everything. Caught by the existing `proxy_reconnects_to_a_restarted_compositor` test failing, not by live testing.

  Fixed: reset `next_host_id` to 2 and re-seed `wl_display`'s mapping in `bump_generation()`; check `fill()`'s return value explicitly. Four new regression tests. Commit `9d2dc8f`.

- 2026-07-30 (follow-up): with the above fixed, a full live run got further but still failed: recreation succeeded (fresh gapless host ids 4-9), but the client's `ack_configure` for our *synthesized* `xdg_surface.configure` (see `recover_state_after_reconnect`, sent straight to the client to force a repaint) forwarded to the real compositor like any other message -- which rejected it, `"wrong configure serial: 1"`, since it never issued that serial itself. Second EOF followed immediately, and this time `gtk4-demo` disconnected instead of surviving.

  Not a wire-encoding or allocator bug this time -- a genuine gap in the recovery design: nothing reconciled an invented client-side serial against the real compositor's own serial tracking. `implementation-constraints.md` says to synthesize the configure, not how to handle the resulting ack.

  **Fix**: `pending_configure_acks: HashMap<u32, u32>` (guest `xdg_surface` id -> pending synthetic serial), threaded through `run_connection` alongside `objects`/`graph`/`grabs`. `recover_state_after_reconnect` records the entry when it sends the synthetic configure; `relay_ready_messages` checks it on every `ClientToHost` `xdg_surface.ack_configure` and, on a match, consumes the entry and drops the message instead of forwarding it. Regression test extended onto `full_reconnect_recreates_surface_chain_and_synthesizes_configure` (asserts the second life's next observed message is the one sent *after* the ack, proving the ack itself never arrived).

  Verified live end to end: crashed labwc, started a replacement on the same socket, watched the proxy recreate the full chain, synthesize+ack the configure without a compositor error, receive a second *real* `xdg_surface.configure`/`ack_configure` pair from the new compositor normally, and `gtk4-demo` stayed alive and connected throughout -- task 14 (live-verify crash recovery) passes.

- 2026-07-30: First real use of `scripts/start-host.sh` + `scripts/start-guest.sh`'s documented two-layer flow (nested `labwc` inside the container, attached to a host `labwc`+`wayvnc` session) -- every prior live test had used a single headless `labwc` directly inside the container instead, so this path had never actually been exercised end to end. Failed immediately: `entrypoint.sh`'s nested `labwc` errored `Could not connect to remote display: No such file or directory`.

  **Root cause**: `scripts/setup-env.sh` never mounted the host's `XDG_RUNTIME_DIR` (`/run/user/<uid>`, where `start-host.sh`'s Wayland socket lives) into the container -- only `$HOME` and `/dev` were shared. The container's own `/run/user/<uid>` was a separate, empty directory created from scratch. Distrobox (the setup this replaced) forwarded the host display socket automatically; the plain-podman replacement never reproduced that specific piece.

  **Fix**: `setup-env.sh` now bind-mounts `/run/user/<uid>` at the same path in the container, alongside a preflight check that the directory exists on the host first. This also made the old root-exec `mkdir`/`chown`/`chmod` step (which created the container's *separate* runtime dir) unnecessary -- removed, since the bind-mounted host directory already has correct ownership by construction (container UID is built to match the host's).

  Verified: recreated the container, confirmed the host's `wayland-0` socket is visible inside it, re-ran `start-guest.sh` -- nested `labwc` connects and creates its own `wayland-N` socket successfully.

- 2026-07-31: While fixing a container-shell prompt that was indistinguishable from the host's own (`hostname` returns the same value on both sides -- `--network host` shares the UTS namespace too), baking a `PS1` customization into the image's `~/.bashrc` had no effect at all. Root cause was bigger than the prompt: `setup-env.sh` mounted `-v "$HOME:$HOME"` -- the *entire* host home directory, not just the project -- so on this dev host, where the host account happens to also be named `stu` (matching what the container's own user was then hardcoded to), the bind mount completely shadowed the image's `/home/stu` with the host's real one. Anything baked into that user's home directory in the image was silently discarded at runtime, and -- the more serious half -- anything the container wrote there would have landed in the real host home directory.

  **Fix**: stopped mounting `$HOME` at all. `setup-env.sh` now mounts only the project directory, at a fixed generic path (`/workspace`) inside the container, matching a standard devcontainer layout. The container's own user was also renamed `stu` -> `dev` (a fixed, generic login name -- only the numeric UID/GID need to match the host, never the username) so nothing about the container depends on whoever's account happens to be building it. Every script that previously computed a host-side absolute path and reused it as a container-side one (`start-guest.sh`'s `entrypoint.sh` invocation, `diagnose.sh`'s self-invocation inside the container) now references the fixed `/workspace` path instead.

  Once `$HOME` genuinely wasn't shared, the original `~/.bashrc` PS1 attempt still didn't work, for an unrelated reason: Ubuntu's own stock `~/.bashrc` sets `PS1` itself further down, after anything sourced earlier (confirmed by first trying `/etc/bash.bashrc`, verifying with a marker variable that it *was* being sourced, and finding Ubuntu's `~/.bashrc` simply overwrote `PS1` afterwards regardless). Fixed by appending to `~/.bashrc` directly so it runs last.

  Verified: rebuilt the container, confirmed `/workspace` holds the project and `$HOME` (`/home/dev`) holds only the stock two-file skeleton, confirmed the host's real `~/.bashrc` is untouched (identical byte for byte before and after), confirmed `cargo build` and the full `start-guest.sh` flow (entrypoint, nested `labwc`, interactive shell landing in `/workspace` as `dev`) all still work, confirmed the `PS1` prefix renders.

- 2026-07-31: Followed up on the intermittent `test-crash.sh` slowdown/failure from the X11-contention investigation (see `diagnose.sh`'s rewrite entry) by disabling XWayland entirely for our own headless test/nested compositor instances -- this project never uses XWayland, so removing it was a real hardening improvement regardless of outcome, not just a debugging experiment.

  Added `scripts/labwc-config/rc.xml` (`<core><xwayland>no</xwayland></core>`), wired into `entrypoint.sh` and `test-crash.sh` (not `start-host.sh`, which runs a real interactive session and should keep labwc's normal config search). First attempt silently did nothing: the explanatory comment inside the XML used `--` (em-dash-style) punctuation, which XML forbids anywhere inside a comment body -- labwc's parser rejected the whole file and fell back to default config with no visible warning beyond a one-line parse error easy to miss in the log. Fixed the punctuation, confirmed live afterwards: no `Xwayland` process spawns at all now (previously left zombie `Xwayland` processes behind every run).

  **However**: this did not fix the underlying intermittent failure. Ran `test-crash.sh` four times in a row with XWayland confirmed fully disabled -- all four still failed the same way, `labwc` alive but never creating its own socket within the timeout. `fuser -v /dev/dri/renderD128` shows the real bottleneck: this host's GPU render node is shared with other, unrelated `labwc`/`Xwayland` sessions outside this project entirely, same ones found in the earlier X11-contention investigation. That's GPU/DRM-level contention, not XWayland-socket contention -- a genuine property of this specific shared host, not something fixable from inside this project. Not chasing further: `diagnose.sh`'s X11-contention view already surfaces this class of problem when it recurs, and `test-crash.sh`'s 20s timeout (already bumped once) stays as a reasonable-effort accommodation, not a guarantee.
